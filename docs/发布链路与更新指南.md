## 三、更新发布流程（以后照这个走）

Registry 中同一 server 的版本**不可重复提交**，任何改动都必须升版。

1. **改代码**，本地验证 `tools/list` 返回 remember / recall / stats / forget 四个工具；若改了工具行为（如新增可选 `namespace`），同步更新两个 README 与 `SERVER_INFO.version`，并做隔离性回归测试。
2. **升 npm 版本**：改 `nebula-memory-mcp/package.json` 的 `version`，**保留** `mcpName: "io.github.yb-zhai/nebula-memory"`（缺这个字段 Registry 会拒收）；`npm publish`。
3. **对齐 server.json**：仓库根目录 `server.json` 的 `packages[0].version` 改成刚发布的 npm 版本；如需更新 server 版本，改顶层 `version`。`description` 必须 ≤ 100 字符。
4. **本地校验**：`mcp-publisher validate server.json`（工具在 `%TEMP%\mcp-publisher-check\`，或用官方 release）。
5. **推送触发发布**：push 到 `main` 后，打 `v*` 标签（如 `v1.3.1`）或在 Actions 页手动 Run workflow 触发 `.github/workflows/publish-mcp.yml`。
6. **验证**：查 Registry 搜索接口，确认 `status: active`、版本和 npm 包版本正确。

工作流用 **GitHub Actions OIDC**（`login github-oidc`）证明 `io.github.yb-zhai/*` 命名空间所有权，无需任何 token。

## 四、踩过的坑（排查备忘）

- **`mcpName` 缺失**：npm 包必须声明且与 `server.json` 的 `name` 完全一致，否则报 `Registry validation failed for package`。1.0.0 因为没有此字段发不上去，1.0.1 才补上。
- **`description` 超长**：`mcp-publisher validate` 实测限制 100 字符，超了返回 422。
- **PAT 权限**：用 PAT 推送 `.github/workflows/*` 需要 `workflow` scope，只有 `repo` 会被 GitHub 拒绝；日常工作用网页登录态或带 workflow 权限的 token 走 API。
- **npm 缓存延迟**：刚发布时版本端点和 `npm view` 都可能短暂 404；**以 packument（`https://registry.npmjs.org/<包名>` 的 `versions` / `dist-tags`）为准**，稍等即同步。曾经 `npm view` 立刻可见（1.0.1），也可能连它都 404（1.1.0），都属正常传播延迟。
- **DNS 抽风**：本机解析 github.com 时常命中不通的 IP，浏览器会自动重试所以感觉流畅，但 git/命令行会超时。临时解法：给 git 指定可用 IP（`140.82.114.4` 等）或临时改 hosts 后立即恢复；`api.github.com` 一直稳定。
- **mcp-submit 的「0 tools」**：那是它的弱静态探测误报，实测 `tools/list` 正常返回四个工具，不用改代码。
