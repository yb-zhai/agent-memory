# 记忆星云插件优化报告

**日期**：2026-11-21
**插件**：dsh-memory-nebula（记忆星云）
**版本跨度**：1.2.29 → 1.3.7

---

## 一、背景

对插件做了一次线上评测，评测报告（架构评审）提出了六大潜在隐患。经逐条核对代码实现，发现评测结论**一半成立、一半与现状不符**。本报告记录对"真实且有性价比"问题的优化过程、实测结果，以及对"被高估/不适用"建议的论证结论。

### 评测结论核对结果

| 评测条目 | 核对结论 | 处置 |
|---|---|---|
| ① 数据一致性与双写冲突 | 部分成立，但主从关系说反了 | 单向镜像加固（1.3.2） |
| ② 召回延迟与打分不可比 | **成立**，最该改 | RRF 融合（1.3.0）+ 并发召回（1.3.1） |
| ③ JSONL I/O 瓶颈 | **不成立**（数据量被高估） | 跳过，实测论证 |
| ④ 成本与隐私泄露 | 成立，但属 Hindsight 侧 | 暂缓（非本插件职责） |
| ⑤ ACT 衰减/LEX 词汇鸿沟 | 属算法设计取舍，非缺陷 | 可选增强，暂缓 |
| ⑥ 运维复杂度 | 成立，但已有缓解 | 顺带修时序 bug |

## 二、已完成的优化

### P0 — RRF 融合打分（1.3.0）

**问题**：本地四臂（`0.55·lexNorm + 0.30·actNorm + 0.15·recency`，0~1 归一化）与 Hindsight 语义分（semantic/keyword/reranker）**不在同一分数空间**。原代码直接 `results.sort((a,b) => b.score - a.score)` 混排，导致 Hindsight 分数天然偏高、淹没本地精准匹配。

**改法**：改为 **RRF（Reciprocal Rank Fusion）**，按来源（本地一组、Hindsight 一组）各自取排名：

```
score_rrf = 1 / (60 + rank)    # k=60
```

**实测对比**（查询「记忆星云 连线 数据链」）：

| 来源 | 原始分 | 排名 | RRF 分 |
|---|---|---|---|
| local | 0.7577 | 0 | 0.0167 |
| hindsight | 1.0970 | 0 | 0.0167 |

改造前 Hindsight 的 1.09 分会把本地 0.75 分全部压下去；改造后两侧第一名同权并列、逐名交替，组内顺序保留。

**配套**（1.3.3）：排序用 RRF、**显示用原始分**（`rawScore`），避免卡片上出现 0.02 这种不可读的排名分。新增 `dispScore()` 辅助函数，三处显示点（召回卡分数、分数条、拼上下文 chip）统一改用它。

---

### P1 — 本地与 Hindsight 并发召回（1.3.1）

**问题**：`MemoryEngine.recall` 串行 `await` 本地 + `await` Hindsight，Hindsight 慢时（内部 30s 超时）会把整体召回拖住。

**改法**：改为 `Promise.all` 并发，并新增 `_recallHindsightBounded()` 用 `requestTimeoutMs`（默认 8s）硬超时兜底：

```js
const [local, hindsight] = await Promise.all([
  this.local.recallFragments(query, opts),   // 保底，必须成功
  this._recallHindsightBounded(query),        // 增强，失败/超时降级 null
])
```

**效果**：整体延迟 = `max(本地, Hindsight)`，且最坏情况 8s 封顶。本地是保底、Hindsight 是增强，后者失败不阻塞主链路。

---

### 镜像一致性加固 — 断点续导（1.3.2）

**问题**：`mirror-hindsight.mjs`（Hindsight → 本地 JSONL 单向镜像）手动运行时，若中途崩溃需用户手动记 `START_OFFSET` 续导，补偿窗口内重启会漏数据。

**改法**：新增 `mirror-state.json` 水位文件：

- 每导完一批（100 条）落盘一次水位（`offset/total/target/bank`）；
- 启动时检测到上次水位 `< total`，**自动从水位续导**（无需手动 START_OFFSET）；
- 导完或到 target 清除水位文件；
- `RESET=1` / 显式 `START_OFFSET` 覆盖水位。

**说明**：评测建议的"sync_pending + worker 指数退避重试"针对的是**双写同步**，但当前架构是**单向镜像**（本地不写 Hindsight），且镜像脚本是手动运行，不引入 worker 定时重试（避免过度设计）。

---

### 冷启动优化（1.3.4 ~ 1.3.6）

**问题**：冷启动到 ready 实测 **5.9s**，其中本地 JSONL 索引重建 2.4s + Hindsight 串行探测 3.5s。

**精确拆解**（profile 计时）：

| 阶段 | 耗时 |
|---|---|
| `_loadNodes`（解析 70,238 行） | 696ms |
| `_loadEdges`（42,230 行） | 105ms |
| `_rebuildDerived`（倒排+邻接） | 1220ms |
| `_loadIndexSnapshotMeta` | 191ms |
| **本地 init 合计** | **~2.4s** |
| Hindsight 串行探测（_probe 1.5s + bank 列表 + stats） | ~3.5s |

**改法**（两处）：

1. `MemoryEngine.init()`：本地 init 完成后立即返回（mode 先置 `local`），Hindsight 探测放后台 `_connectHindsightBackground()`，完成后自动切 `hybrid`；
2. `server.js` 的 `instance.init()`：`legacy.maybeRefresh()`（含 Hindsight 4 个元数据请求，同步等 ~1.5s）改成后台触发不 await。

**顺带修复**：`LocalBackend.stats()` 在 `close()` 后 `this.mem` 为 null 时，后台探测任务的 `refreshStats` 抛 `Cannot read properties of null (reading 'stats')` —— 加空判防御。

**效果**：冷启动 **5.9s → 2.89s（-51%）**，且 ready 后自动从 local 升 hybrid（日志确认链路正确、无报错）。

---

### P2 — 面板加载态（1.3.7）

**问题**：冷启动 ~2.9s 期间面板无反馈，用户体感"卡顿"。

**改法**：新增 `#loading-overlay` 覆盖层（青色旋转环 + 「正在唤醒本地记忆 …」+ 副标题「重建索引 · 连接 Hindsight」），半透明底让面板骨架隐约透出。`S.booted` 标志在 SSE `hello` 帧或首次 `/state` 成功时置 true，数据一到 0.45s 淡出并移除。

**实测**：CDP 双时点截图确认，加载态 50ms 时清晰显示、3.55s 后正确淡出。

## 三、论证后跳过的优化

### P1（原）— 倒排索引落盘（不推荐）

评测建议"启动先加载缓存的 index.json、后台重建热替换"，声称收益"2.4s → <1s"。

**实测论证**：`_rebuildDerived` 拆解后发现，**能被落盘索引省掉的只有倒排构建（463ms）+ 邻接（16ms）**，而 `_loadNodes`（696ms）和 `_tfFor`（531ms）**必须读原始 JSONL + 现算 TF，落盘索引帮不上**。

- 净收益 ≈ 480ms - 读盘开销 ≈ **250~380ms（12~16%）**，远低于评测声称的 1.4s；
- 成本：index.json 从 19MB 膨胀到 ~27MB，且要动 store.cjs 最核心的索引读写路径，引入"多版本一致性校验 + 后台重建热替换"，任何漏判都会导致**召回结果静默错误**。

**结论**：风险远大于收益，跳过。冷启动经 P0 已降到 2.89s，边际收益递减。

### SQLite 重构（评测建议强烈推荐）

评测建议把 JSONL 换成 SQLite（WAL 模式）。

**实测论证**：本地实际数据量 **nodes 70,238 行 / edges 42,230 条**（评测说的"95 万边"是 Hindsight 侧 Postgres 的，不是本地），远未到 JSONL 的极限；且本地无多进程并发写场景。属于过早优化，跳过。

## 六、追加优化（1.3.8）

基于第二轮反馈的三个问题点，逐点分析后落地：

### 6.1 PIN 置顶固定权重（importance=1.0 即永固）

**问题**：用户"我的 API 密钥是 xxx""以后叫我老板"这类关键事实，会因"30 天没聊"被 ACT 衰减到 0。

**方案**：不采用评测建议的 `is_pinned` 独立字段（本地引擎是规则式抽取，没有任何写入路径能识别"这是关键事实"并置位该字段，加了就是死字段），改为 **`importance=1.0` 即永固** —— 复用现有 importance 通道，抽取层/Hindsight 把关键事实 importance 设为 1.0 即自动 pin。

**改动**（三处衰减点全部跳过）：

| 位置 | 文件 | 改动 |
|---|---|---|
| FSRS 遗忘曲线 | `dynamics.cjs:retention` | `importance≥1.0` 返回 1 |
| 词法打分 decay | `store.cjs` | `importance≥1.0` 时 decay=1 |
| consolidate importance 衰减 | `store.cjs` | `importance≥1.0` 跳过衰减 |

**实测**（365 天没访问）：

```
置顶(importance=1.0) retention: 1.0000   ✓ 永不遗忘
普通(importance=0.5) retention: 0.0000   衰减到 0
consolidate 后置顶 importance: 1.0 不变   普通: 0.5 → 0.02
```

### 6.2 加载态分阶段提示

**问题**：1.3.7 的加载态是单一文案，无法区分"本地卡了"还是"在等外脑"。

**改法**：加载态文案跟着真实状态走：

```
booted=false            → 「正在唤醒本地记忆 …」
booted=true 且外脑未连  → 「本地记忆已就绪，正在连接外脑 …」
外脑连上 / 纯 local 3s 兜底 → 淡出
```

加了 3s 强制淡出兜底，避免纯 local 模式（Hindsight 永远没连）卡在「连接外脑」不消失。

### 6.3 Hindsight 召回超时 8s → 3s

**问题**：8s 硬超时对 Promise.all 兜底够，但外脑 3s 没回时用户注意力已分散。

**改法**（第一步，低成本）：新增独立配置 `hindsightRecallTimeoutMs`（默认 3s，可 `HINDSIGHT_RECALL_TIMEOUT_MS` 覆盖），与通用 `requestTimeoutMs`（8s，仍用于 graph/stats）解耦。外脑 3s 没回就降级纯本地。

**两段式广播（第二步）留作后续独立迭代**：需要 server 侧"本地先发 + Hindsight 后 append"两次广播 + 面板侧增量合并状态机，工作量和回归风险中等，单独做而非夹在常规迭代里。

## 八、结论

针对评测报告的改进已全部收尾。真实且有性价比的优化均已落地：

- **召回质量**：RRF 融合纠正了本地/Hindsight 分数不可比的问题（1.3.0）；
- **召回性能**：并发召回 + 硬超时，Hindsight 慢/挂起不再拖累本地（1.3.1）；召回超时进一步收紧到 3s（1.3.8）；
- **数据一致性**：镜像水位 + 断点续导，堵住补偿窗口漏数据（1.3.2）；
- **记忆可靠性**：importance=1.0 即永固，关键事实不受时间衰减（1.3.8）；
- **冷启动**：探测并发化，5.9s → 2.89s（1.3.6）；
- **体验**：加载态反馈 + 分阶段文案，等待期有明确进度（1.3.7 / 1.3.8）。

评测中"SQLite 重构""倒排索引落盘"等建议经实测论证为**被高估或过早优化**，已明确跳过并记录理由；"is_pinned 字段"方案经论证改为"importance=1.0 永固"（避免死字段），"流式返回"拆为"先收紧超时"（已做）+ "两段式广播"（留作独立迭代）。
