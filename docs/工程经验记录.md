# 工程经验记录

本文件收录开发过程中踩过的坑与已验证的正确做法，供后续迭代与协作者参考。
每条都记录**错误做法、失败现象、根因、正确做法**四要素——只写"别这么做"没有用，
下次照样会踩，必须写清为什么不这么做。

## Git 与命令

### 1. `git hash-object --path=<p> <file>` 漏写 `--` 会算出错误的哈希

**错误做法**

```bash
# ❌ 缺少 --，--path 会把后面的文件名当成自己的参数值吞掉
git hash-object --path=README.md README.md
```

**失败现象**

该命令不报错，正常输出一个 40 位哈希，但**这个哈希不是对的**。
拿它与 `git rev-parse HEAD:<file>` 对比会显示不一致，于是误判「文件有未提交改动」，
进而可能做出错误的操作（如重新提交、回滚、甚至改写历史）。

**根因**

`--path=<p>` 是一个带值的选项。后面直接跟文件路径时，Git 的参数解析会把它当作
`--path` 的值的一部分或额外参数，导致 `hash-object` 实际上没有对预期的文件做
`clean` 过滤器归一化（换行符转换、编码处理等），算出的哈希与仓库存储的哈希不可比。

**正确做法**

```bash
# ✅ 用 -- 明确分隔「选项」与「路径」
git hash-object --path=README.md -- README.md
```

**更推荐的做法**

判断「文件到底有没有改」时，**不要自己算哈希**，直接用 Git 自己的判定：

```bash
git status --short -- <file>     # 空输出 = 无变更（唯一权威判定）
git diff -- <file>              # 直接看内容差异
git diff --ignore-cr-at-eol -- <file>   # 排除换行符差异干扰
```

### 2. Windows 上 `core.autocrlf=true` 会让哈希比对出现"假差异"

**失败现象**

工作区文件与 `HEAD` 版本**内容完全一致**，但字节级哈希不同；
`git diff` 却显示"无差异"，`git status` 也显示干净。

**根因**

Windows 上 `core.autocrlf=true` 时：

- 检出：仓库内的 LF → 工作区 CRLF
- 提交：工作区 CRLF → 仓库内 LF

所以工作区字节与仓库存储字节**天然不同**，直接比对原始哈希必然不一致。
用 `git hash-object` 且正确应用了 clean 过滤器时，才会归一化后一致。

**正确做法**

- 判断有无改动：**以 `git status` 为准**，不要自己算哈希；
- 必须比对哈希时：用 `git hash-object --path=<p> -- <file>`（走 clean 过滤器）；
- 判断差异是否只是换行符：`git diff --ignore-cr-at-eol` 或 `--ignore-all-space`。

### 3. `git diff` 加窄过滤条件会漏看改动行

**错误做法**

```bash
# ❌ 过滤条件过窄，会漏掉不含该模式的实际改动行
git diff -- file.md | Select-String -Pattern '^\+[^+].*某关键词'
```

**失败现象**

明明改了两处，`diff` 输出里只看到一处，于是误以为「改动没生效」或「只改了一半」。

**正确做法**

先看**完整的 diff 输出**确认范围，再用过滤条件做辅助检索：

```bash
git diff -- <file>                  # 先看全貌
git diff --numstat -- <file>        # 看增删行数（如 2 2 表示两增两删）
```

`--numstat` 特别有用：它直接给出增删行数，能立刻判断"应改 N 处、实改 N 处"是否吻合。

### 4. `git rebase` 冲突中的 `--ours` / `--theirs` 与 merge 语义相反

**错误做法**

```bash
# ❌ 在 rebase 中想「取远端最新版本」，于是用 --theirs
git checkout --theirs -- <file>
```

**失败现象**

取到的**不是** `origin/main` 的最终状态，而是**正在回放的那个旧提交**当时的快照。
后果可能是版本号倒退、后续功能代码被删除（本次实际发生了 `server.json` 从 1.5.0
退回到 1.4.0、`mcp-server.mjs` 丢失 `compact` 子命令）。

**根因**

- **merge 时**：`ours` = 当前分支，`theirs` = 被合入的分支；
- **rebase 时**：身份对调，`ours` = **上游分支**（你 rebase 到的目标），
  `theirs` = **正在回放的那个提交**。

而且无论哪种情况，都**不是**分支的"最终状态"——只是该次冲突点的三方快照。

**正确做法**

1. **不要凭 `--ours` / `--theirs` 直觉做决定**，逐个冲突块看实际内容；
2. 判断"某功能是否已存在于目标分支"时，**直接查目标分支**：

```bash
git show origin/main:<file> | grep -n "<关键代码>"   # 目标分支里到底有没有
```

3. 若本地历史与远程已大规模分叉、逐个回放代价高，改用**单提交重放**：

```bash
git branch backup-xxx                 # 先备份原历史
git reset --soft origin/main          # 指针对齐远程，文件内容不动
# 审查暂存区差异 → 剔除无意义变更 → 合并为一个提交
git commit -m "..."
```

**事后立刻核对内容**是发现此类错误的唯一可靠手段：提交完成后，
用 `git show --stat` 和关键文件内容验证，不要假设命令做对了。

### 5. `reset --soft` 后需警惕"格式污染"文件

**失败现象**

`reset --soft` 后，一些**内容根本没变**的文件出现在暂存区里，
`git diff --stat` 显示上百行变动（本次 `README.md` 显示 518 行、`package.json` 102 行）。

**根因**

文件被编辑器或工具重写过，产生了**纯空白 / 缩进 / 行尾换行符**的差异。
这类"格式污染"提交进去后，会让 PR diff 出现大量无意义变动，掩盖真正的改动。

**正确做法**

```bash
# 用 --ignore-all-space 判断实质差异
git diff --cached --ignore-all-space origin/main -- <file>
```

实质差异为 0 行的文件，直接恢复成目标分支版本：

```bash
git checkout origin/main -- <file>
```

### 6. PowerShell 的 `Set-Content -Encoding UTF8` 在 5.1 下会写入 BOM

**失败现象**

用 `Set-Content -Encoding UTF8` 写出的文件带 UTF-8 BOM（字节头 `EF BB BF`），
导致下游工具解析失败。本次实际影响：`~/.ssh/config` 第一行变成 `\357\273\277host`，
`git fetch` 报 `Bad configuration option: \357\273\277host`。

**根因**

Windows PowerShell 5.1 的 `-Encoding UTF8` 指"带 BOM 的 UTF-8"，
与 PowerShell 7+ 的行为不同。

**正确做法**

```powershell
$enc = New-Object System.Text.UTF8Encoding($false)   # false = 不写 BOM
[System.IO.File]::WriteAllText($path, $content, $enc)
```

写配置文件后**校验字节头**：

```powershell
$b = [System.IO.File]::ReadAllBytes($path)
"BOM: $($b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF)"
```

同理，`Get-Content` / `Set-Content` 处理中文路径时还可能出现八进制转义，
用 `git -c core.quotepath=false` 可让 Git 输出可读路径。

### 6.5 改写已有文件前必须检测原编码，否则全文中文会毁掉

**这是本会话重复犯的错误，已造成两次文件损坏。**

**错误做法**

```powershell
# ❌ 只检查了 BOM，就直接用 UTF-8 读写
$b = [System.IO.File]::ReadAllBytes($f)
"前3字节: {0:X2} {1:X2} {2:X2}" -f $b[0],$b[1],$b[2]
$txt = [System.IO.File]::ReadAllText($f)   # 默认按 UTF-8 读
[System.IO.File]::WriteAllText($f, $newTxt, (New-Object System.Text.UTF8Encoding($false)))
```

**失败现象**

文件里**全部中文变成乱码**，形如：

```
# 鈹€鈹€ 鍚姩鏍囪锛?026-11-11 鍔狅級鈹€鈹€
# 瀹炴祴锛?1-17~11-18 涓ゅぉ锛?63 娆¤皟鐢?/ 10.6M 杈撳叆 tokens锛?
```

同时 `PSParser` 报语法错误（`字符串缺少终止符`、`缺少右 }`）。
从 diff 看是「全文件 226 行都变了」——**这就是危险信号**：只改了 1 行配置，不可能有 200+ 行差异。

**根因**

Windows PowerShell 5.1 **读文件时如果发现没有 UTF-8 BOM，会按系统 ANSI(GBK) 解码**。
一个原本是「UTF-8 带 BOM」的文件，被工具以「UTF-8 无 BOM」写回后：

1. BOM 丢了 → PowerShell 下次按 GBK 解析
2. 中文 UTF-8 字节被当成 GBK 双字节 → 乱码
3. 乱码里可能含有引号、括号等，**直接破坏脚本语法**

**正确做法**

改写任何已有文件之前，**三步都要做**：

```powershell
# 第 1 步：检测编码（不只看 BOM，要试解码）
$b = [System.IO.File]::ReadAllBytes($f)
$hasBom = ($b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF)
$isUtf8 = $true
try {
    [void](New-Object System.Text.UTF8Encoding($false, $true)).GetString($b)
} catch { $isUtf8 = $false }
"BOM=$hasBom  合法UTF8=$isUtf8"

# 用两种编码各读一行中文，看哪个正常
[System.Text.Encoding]::UTF8.GetString($b)                 # UTF-8 读法
[System.Text.Encoding]::GetEncoding('GBK').GetString($b)   # GBK 读法

# 第 2 步：用原编码读，写回时保持同一编码（含 BOM 状态）
$enc = New-Object System.Text.UTF8Encoding($hasBom)   # 与原文件 BOM 状态一致
$txt = [System.IO.File]::ReadAllText($f, $enc)
$newTxt = $txt -replace [regex]::Escape($old), $new
[System.IO.File]::WriteAllText($f, $newTxt, $enc)

# 第 3 步：写后立刻校验
```

**改完必须做的三项校验**（缺一不可）：

```powershell
# ① BOM 状态未变
$b2 = [System.IO.File]::ReadAllBytes($f)
"BOM 仍为: $($b2[0] -eq 0xEF -and $b2[1] -eq 0xBB -and $b2[2] -eq 0xBF)"

# ② 语法错误为 0
$err = $null
[System.Management.Automation.PSParser]::Tokenize((Get-Content $f -Raw), [ref]$err) | Out-Null
[System.Management.Automation.Language.Parser]::ParseFile($f, [ref]$null, [ref]$null) | Out-Null
"语法错误: $($err.Count)"

# ③ 与备份的差异只有预期那几行
Compare-Object (Get-Content $bak -Encoding UTF8) (Get-Content $f -Encoding UTF8)
```

**关键判据：差异行数必须与预期改动量匹配。**
改 1 行配置，diff 却显示 200+ 行 → **100% 是编码灾难，立刻用备份回滚**，不要试图修补。

**改任何配置文件前先 `Copy-Item` 备份并 `Get-FileHash` 记录**，
出问题时 `Copy-Item $bak $f` 回滚后哈希应完全一致。

### 6.6 判断「服务是否重启」要比 pid，不要看健康检查是否超时

**错误做法**

```powershell
# ❌ 用「健康检查是否可达」来判断服务有没有被重启
try { Invoke-RestMethod 'http://127.0.0.1:8888/health' -TimeoutSec 3 } catch { "服务挂了/重启了" }
```

**失败现象**

明明服务从头到尾没动过（pid 完全一致），却因为一次健康检查 3 秒超时而误判为「重启了」，
进而去查不存在的崩溃，浪费大量时间。

**根因**

健康检查端点本身要**获取一个数据库连接**才能响应。
批量任务运行时连接池被占（实测 `in_use=14`），`/health` 需要排队，3 秒超时不够。
Hindsight 的日志里明确写着这个坑：

```
The pool is likely saturated; /health can stall on connection acquisition
while the event loop is free.
```

**正确做法**

判断重启的唯一可靠判据是**进程标识是否变化**：

```powershell
# 执行动作前
$before = (Get-NetTCPConnection -LocalPort 8888 -State Listen).OwningProcess

# ... 执行动作 ...

# 执行动作后（给足缓冲时间）
Start-Sleep -Seconds 3
$after = (Get-NetTCPConnection -LocalPort 8888 -State Listen).OwningProcess
"是否重启: $($before -ne $after)"
```

健康检查只用来判断**服务是否可以服务请求**，且超时时间要给足（批量任务运行时建议 ≥8 秒）。

**同类陷阱**：任何「有副作用但需要探测」的场景（端口、健康检查、锁文件），
探测失败都只说明**那一刻**不可用，不等于状态发生了变化。

### 6.7 阈值开关必须加迟滞（hysteresis），否则会在阈值附近抖动

**错误做法**

```powershell
# ❌ 单阈值：超过就开、低于就关
$overload = $pending -gt 20
if ($overload) { return 'true' }
if ($pending -le 20) { return 'false' }
```

**失败现象**

被控对象在一个区间内自然波动时（实测积压在 0~38 之间来回），
每次跨过阈值就切换一次状态。如果切换状态需要重启整个服务，
就会变成一天重启十几次。

实测数据（一天的积压采样）：

```
21:07  pending=6   → 关
21:22  pending=18  → 关
21:37  pending=38  → 开    ← 越过 20
21:52  pending=0   → 关    ← 又越过 20
22:07  pending=4   → 关
22:52  pending=16  → 关
```

**根因**

单阈值没有「记忆」：状态只由当前采样值决定，而采样值本身在噪声范围内波动。
这是控制理论里的经典 **flapping（抖动）**。

**正确做法**

**双阈值 + 连续确认**（迟滞）：

```powershell
# 开启：高于高水位才开
# 关闭：低于低水位，且连续 N 次采样都低才关（防瞬时抖动）
$highThr = 40
$lowThr  = 5
$confirm = 2

if ($pending -gt $highThr) { return 'true' }
if ($pending -lt $lowThr) {
    if ($idleStreak -ge $confirm) { return 'false' }   # 连续确认才关
    return 'true'                                      # 否则保持
}
# 中间地带：保持当前状态，不动
return $currentState
```

**关键设计**：中间地带的判定必须是「**保持现状**」而不是「重新计算」。
这样只有当状态真的需要改变时才动作，切换次数下降一个数量级。

**验证方法**：执行一次判定后，检查**进程 pid 是否变化**（见 6.6），
而不是只看逻辑输出的结论对不对。

## 性能测量

### 7. 1ms 量级的延迟不要用单次少量采样下结论

**错误做法**

```javascript
// ❌ 50 次采样、单轮、无预热
for (let i = 0; i < 50; i++) { /* 计时 */ }
const p50 = arr[25]
```

**失败现象**

实测出现过「扩展开启比关闭**快 15%**」这类物理上不合理的值；
换个时间再跑，结论又反过来。这类数字一旦写进报告，**无法复现，也无法对质**。

**正确做法**

- 每态至少 200 次采样、跑多轮取中位数；
- 多轮之间**交替顺序**（偶数轮先 A、奇数轮先 B）抵消机器的负载漂移；
- 测量前**预热**若干次，让 JIT 与索引进入热态；
- 输出**逐轮数据**而非只给汇总，便于看出噪声幅度；
- 1ms 量级的结论只写趋势（「开销远小于 1ms」），**不写精确小数**。

参考实现：`scripts/bench-query-expansion-overhead.mjs`。

## 数据与报告

### 8. 评测脚本覆盖整个结果文件会静默丢数据

**错误做法**

```javascript
// ❌ 每次运行都重置全部字段
const out = { when: now, bench: null, freshness: null }
```

**失败现象**

只跑其中一项（如 `--freshness`）时，另一项（`bench`）被覆盖成 `null`，
**原本的评测结果静默丢失**，报告里的数字从此没有原始数据可核验。

**正确做法**

```javascript
let prev = {}
try { prev = JSON.parse(fs.readFileSync(outFile, 'utf8')) } catch { /* 首次运行 */ }
const out = {
  bench: DO_BENCH ? await evalBench() : (prev.bench || null),
  freshness: DO_FRESH ? await evalFreshness() : (prev.freshness || null),
  benchRunAt: DO_BENCH ? now : prev.benchRunAt,
  freshnessRunAt: DO_FRESH ? now : prev.freshnessRunAt,
}
```

**要点**：未重跑的字段保留旧值，并**为每个数据集单独记录运行时刻**——
两个数据来自不同批次运行时，共用一个 `when` 时间戳是误导性的。

### 9. 聚合值落盘前必须归一化

**错误做法**

```javascript
// ❌ byType 里存的是累加值，落盘后无法直接使用
byType[type].mrr += 1 / rank
return { byType }
```

**失败现象**

JSON 里存着 `mrr: 127.33` 这类数字（是倒数和，不是均值）。
控制台打印时除了 `n` 所以看起来正常，但**读 JSON 的人会直接误读**。

**正确做法**

落盘前统一归一化：

```javascript
byTypeOut[t] = { n, hit, recall: hit / n, mrr: mrrSum / n }
```

所有比率字段在 JSON 里都应是 0~1 的均值语义，与控制台展示口径一致。

## 网络与凭据

### 10. remote URL 里内嵌 token 是隐患，改用 credential helper

**错误做法**

```
https://user:ghp_xxxxxxxx@github.com/owner/repo.git
```

**风险**

- token 明文保存在 `.git/config`，任何能读该文件的人都能拿到；
- 会出现在 shell history、日志、错误信息中；
- 备份 / 复制仓库目录时一并泄露。

**正确做法**

```bash
git remote set-url origin https://github.com/owner/repo.git   # 去掉凭据段
git config --global credential.helper manager                 # 交给系统凭据管理器
```

移除 URL 中的 token **不等于** token 已失效——**仍需去平台吊销**。
吊销后清理本地缓存：`printf "protocol=https\nhost=github.com\n\n" | git credential reject`。

### 11. HTTPS 被重置但 SSH 正常时，优先走 SSH

**失败现象**

```
error: RPC failed; curl 56 Recv failure: Connection was reset
fatal: expected flush after ref listing
```

同时 `Test-NetConnection github.com -Port 443` 显示"可达"。

**判读要点**

- 出现 `ref listing` 说明 **TLS 握手已成功、认证已通过**，服务器已开始返回数据，
  连接是**传输中途**被中断的——**不是认证失败**（认证失败会是 401 / `Authentication failed`）；
- TCP 层可达不代表应用层可用：`Test-NetConnection` 只握手，不代表 HTTP 能通。

**正确做法**

```bash
ssh -T git@github.com      # 先用 SSH 验证通道质量
git remote set-url origin git@github.com:owner/repo.git
```

## 进程与资源

### 12. 「探活超时 → 换端口重试」会静默累积出多个常驻实例

**这是本项目实际踩过的坑：一天内积累 12 个实例，吃掉约 5 GB 内存和 6 个核的 CPU。**

**错误做法**

```javascript
// ❌ 探不到就认为端口空闲，撞墙就换下一个端口
for (let port = firstPort; port < firstPort + 12; port++) {
  const existing = await probeService(port)        // 超时只有 600ms
  if (existing) return reuse(existing)             // 探到了就复用
  const server = new Server({ port })
  try { await server.listen() }
  catch (e) { if (e.code === 'EADDRINUSE') continue; throw e }  // 撞墙就换端口
}
```

**失败现象**

- 端口从 8898 一路递增到 8909，**12 个实例并存**；
- 每个占约 500 MB 内存，持续空转 CPU（12 个进程 5 秒内合计消耗 32 秒 CPU）；
- 数据目录留下大量 `index.json.tmp-*`（每个 20 MB），是并发写索引的残留；
- 表现是「插件越用越慢、内存越用越高」，但**日志里没有任何报错**。

**根因**

两个看似合理的策略组合成了灾难：

1. **探活超时过短**——已有实例在忙（回写 24 MB 的索引文件）时，
   `/healthz` 响应会超过 600ms，探测拿不到应答；
2. **探测失败被当成「端口空闲」**——实际上端口是被一个**繁忙但健康**的实例占着；
3. **EADDRINUSE 时 continue 换端口**——listen 撞墙后换到 +1 端口重新成功，
   于是「插件重启一次 = 多一个常驻实例」。

单看每一步都不算错：超时 600ms 是合理值，换端口重试是常见容错。
**但「探测失败」和「端口空闲」是两件事，把它们等同起来就会持续生产实例。**

**正确做法**

**先区分三种状态，再决定动作：**

```javascript
const existing = await probeService(firstPort, 3000)   // ① 超时给足（≥3s）
if (existing && existing.service === SERVICE) return reuse(existing)   // ② 健康 → 复用

const server = new Server({ port: firstPort })          // ③ 只认配置端口，不盲试
try { await server.listen() }
catch (e) {
  if (e.code === 'EADDRINUSE') {
    // 端口被占但探不到健康应答 = 旧实例正在启动或已失联。
    // 再起一个只会加剧「多实例写同一份数据」，必须退出。
    throw new Error('port in use but no healthy instance responded; refusing to start a second one')
  }
  throw e
}
```

**三条原则**：

| 原则 | 说明 |
|---|---|
| **一个服务只应有一个实例** | 单实例是常态，不是限制。多实例只在明确设计为集群时才成立 |
| **探测失败 ≠ 资源空闲** | 「连不上」和「没人占用」是完全不同的判断 |
| **端口冲突应退出，而非迁移** | 迁移会掩盖问题；退出让插件宿主/管理员看到并处理 |

**排查方法（发现同类问题）**

```powershell
# 同一服务是否有多实例
Get-Process -Name 'node' | ForEach-Object {
  $cmd = (Get-CimInstance Win32_Process -Filter "ProcessId=$($_.Id)").CommandLine
  if ($cmd -match '<服务名>') {
    $port = (Get-NetTCPConnection -OwningProcess $_.Id -State Listen -EA SilentlyContinue).LocalPort
    "$($_.Id) port=$port mem=$([math]::Round($_.WorkingSet64/1MB))MB"
  }
}
```

**判据：端口连续递增（8898, 8899, 8900…）几乎必然是这类 bug 的指纹。**
正常服务不会自己去占相邻端口。

**「僵死残留」与「活跃多余」要分清**

本次最初怀疑是僵死进程，采样后发现**每个都在真实吃 CPU**——它们是活跃的多余实例，不是僵尸。
判断方法：隔 5 秒采两次 CPU 时间，增长 >0.5s 即在真干活。
