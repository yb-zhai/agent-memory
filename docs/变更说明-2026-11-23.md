## 一、做了什么

今天这两件事，一句话概括：

1. **给"记忆召回准不准"建立了一套可核验的证据链**——报告、评测脚本、原始数据、口径说明四件套入库，报告里每个数字都能回溯。
2. **落地了查询扩展功能**——用三路补偿解决本地引擎"跨表述召回差"的老问题，并把效果量化出来。

两者是配套关系：**功能是本体，报告是它的证据**。

## 二、核心结论（给没时间看细节的同学）

| # | 结论 | 数字 |
|---|---|---|
| 1 | **双引擎融合（RRF）最优** | 93.0% Recall@20，比纯本地 87.0% 高 6 个百分点 |
| 2 | **查询扩展大幅提升召回** | 64.0% → 88.0%（+24pp），拼音纠错单项 +37.5pp |
| 3 | **本地引擎新鲜度是杀手锏** | 写入→可召回 1~4ms，Hindsight 需 43~65s |
| 4 | **本地延迟阈值在 10 万条** | p50 从 13ms（2.4万）涨到 1.75s（50万） |
| 5 | **本地引擎是欠费兜底** | LLM 余额耗尽时 Hindsight 写入全挂，本地照常工作 |

**最重要的一条**：结论 1 说明**双引擎组合本身是有效的**——RRF 融合在所有难度档位都优于任一单引擎，尤其纯语义档（本地 75.6% → 融合 87.8%）。

## 三、代码改动

### 3.1 查询扩展三路补偿（`2b79c92`）

**问题**：本地引擎词法臂此前只做原始 query 的 bigram 匹配，跨表述场景召回率偏低
（实测 near 87.5% / mid 37.5% / far 33.3%）。

**方案**：三路可独立开关的补偿。

| 模块 | 解决什么 | 缺省 |
|---|---|---|
| `memory/typo-fix.cjs` | 拼音错别字/音近字纠正（国内用户高频错误源） | 开 |
| `memory/synonyms.cjs` | 同义词/上下位扩展（「供应商」↔「铸造厂」，32 个概念组） | 开 |
| `memory/profile-recall.cjs` | 画像反哺（个人化提问并入画像关键词） | 开 |

开关：`options.fixTypos` / `expandSynonyms` / `profileBoost`。

**注意一个实现细节**：`recall()` 与 `recallFragments()` 是两条独立路径，**两处都接入了扩展**——否则 MCP/API 侧会享受不到。

### 3.2 Hindsight 召回写回 `recall_trace`（`lib/engine.mjs`）

恢复 `brain_dynamics.py` 的 hebb/prune 数据源。legacy `live_server` 停用后该表断更、赫布链路空转。写入为 fire-and-forget，失败不影响召回。

### 3.3 评测工具链（新增 7 个脚本）

| 脚本 | 用途 |
|---|---|
| `bench-4groups.mjs` | 三组召回对比（100 题） |
| `cross-paraphrase-50.mjs` | 查询扩展效果（50 题） |
| `eval-longmemeval.mjs` | LongMemEval 学术基准 + 新鲜度 |
| `bench-query-expansion-overhead.mjs` | 扩展开销基准（5 轮×200 次） |
| `verify-optimization.mjs` | 31 项回归验证 |
| `bench-scale.mjs` / `gen-fast.mjs` | 容量压测（既有） |

## 四、过程中修掉的问题（值得知道）

做完不算完，复核阶段发现并修了几个**数字本身对、但会误导人**的问题：

### 4.1 一处数据差点永久丢失

`eval-longmemeval.mjs` 每次运行都会把 `bench` 和 `freshness` **同时重写成 null**。上次跑 `--freshness` 就把 LongMemEval 的 500 题结果冲掉了。

**已修**：改为读回并保留未重跑的那一侧，两者各带独立时间戳（`benchRunAt` / `freshnessRunAt`）。LongMemEval 已重跑并留存。

顺带修了 `byType.mrr` 存成倒数和（如 127.33）未归一化的问题。

### 4.2 §2.4 的开销数字不可复现

原报告写「1.23 → 1.29 ms（+0.07 ms）」。这数字来自单轮 50 次采样、无预热，**1ms 量级下噪声极大**——复跑甚至出现「开启反而快 15%」。

**已换**：新基准（5 轮 × 200 次、OFF/ON 交替、带预热）得出 **0.98 → 1.01 ms（+0.03 ms / +3%）**，并注明逐轮 Δp90 在 −1.36 ~ +0.86 ms 波动，**只有"开销远小于 1ms"这个结论稳健**。

### 4.3 多处口径问题已标注

| 数据 | 问题 | 处理 |
|---|---|---|
| G2 Hindsight 召回 50.0% | 题库偏向词面匹配，非其真实水平 | 标 ⚠️¹，明确**不可对外引用** |
| LongMemEval 99.8% | oracle 版（3 会话/题），非完整 haystack | 标 ⚠️，需注明版本 |
| §5 10万/50万容量 | **合成库**（程序化词表 + 随机边） | 标 ⚠️，**仅看趋势** |
| §2 与 §1 | 两套不同题库，百分比不可横向比 | 加醒目提示 |
| typo 档 +37.5% | 仅 8 题，单样本 ±12.5pp | 加样本量提醒 |

### 4.4 移除 G3 两阶段组

原「G3 = Hindsight 召回 → 本地重排」属重排实验，**不属双引擎项目范围**。已从报告、脚本、原始数据中彻底移除，G3 现指 RRF 融合。

## 五、给团队使用者的三句话

1. **报告看 `docs/召回效果实测报告.md`**，§7「对外引用须知」是必读——里面有白名单/黑名单，哪些数字能对客户讲、哪些只能内部比较。
2. **要复现任何数字**，§8 有「原始数据 ↔ 章节对应表」，每个数字对应一个 JSON 文件。
3. **要测扩展开销**，用 `bench-query-expansion-overhead.mjs`，**不要**用 `verify-optimization.mjs` 的性能段（已加注释说明原因）。

## 六、已知限制（不藏着）

- **LongMemEval 用 oracle 版**，无法对标官方完整 haystack 版数字，真实干扰下会显著下降（未测）；
- **Hindsight 单引擎数字口径偏向本地**，只能内部同口径比较；
- **容量压测的高规模档是合成库**，绝对延迟不等于真实数据表现；
- **词表人工维护**，新行业术语需自行追加 `setUserSynonyms()`；
- **未测英文/多语言**场景。
